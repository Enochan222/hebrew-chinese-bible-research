# Product Intent and Requirements Coverage Audit

Date: 2026-10-03
Status: **CURRENT VALIDATION RECORD**

## 1. Audit question

Could a competent developer or researcher who has no access to prior chat history open this repository and accurately explain:

- what product is being built;
- who it is for;
- what the core scholarly workflow is;
- which features are mandatory;
- which sources are foundational;
- what AI may and may not do;
- what public/commercial rights constraints apply;
- what BYOK means;
- what Research Pro is;
- what remains intentionally undecided;
- which document has authority when files disagree?

Before this audit, the answer was only partially yes.

The architecture was unusually detailed, but the product intent was distributed across README, evidence policy, platform architecture, Research Pro, source inventory, staging plan, security and earlier conversations.

The repository now uses `PROJECT_CHARTER.md` as the canonical product-intent authority.

## 3. What was unclear before this audit

### 3.1 Product purpose was inferable, not canonical

The repository strongly described architecture but required synthesis across several files to understand the final product.

Fix:

- created root-level `PROJECT_CHARTER.md`;
- made it the first product-intent authority in README and the architecture manifest.

### 3.2 Whole-Bible scope was not explicit enough

Source-gap documents mentioned whole-Bible coverage, but a builder could reasonably mistake the pilot/fixture passages for the product's intended permanent scope.

Fix:

- whole Hebrew Bible is now the explicit long-term canonical coverage target;
- fixtures/pilot books are implementation staging only.

### 3.3 The project's own Chinese rendering was under-specified

Existing documentation clearly modelled translation witnesses and user drafts, but it was possible to implement the app without a distinct reviewed project rendering.

Fix:

- a reviewed/versioned project Chinese rendering is now explicit;
- it is separate from external witnesses and user drafts;
- it must be linked to TranslationDecision and ResearchRelease.

### 3.4 Drive priority versus rights could be misunderstood

The user-supplied scholarly library is central, but not every file can necessarily be indexed or sent to a model.

Fix:

- the Drive library is mandatory as a curated scholarly research base;
- processing route remains operation-specific and rights-controlled;
- restricted machine processing does not demote scholarly importance.

### 3.5 BYOK could be over-read

Public BYOK rules could be interpreted as prohibiting all private research infrastructure credentials.

Fix:

- BYOK is explicitly a public/user-facing runtime rule;
- private authoring infrastructure may use separately managed operator credentials;
- no such credential may be embedded in or become fallback for the public app.

### 3.6 Status/governance text had drift

The staging plan still contained an older implication that implementation must wait for the entire v1.1 freeze.

Fix:

- Core Database Spike gate, Core freeze, Research Pro freeze and BYOK shipping gate are now distinct;
- README authority list was aligned to `architecture/manifest.json`.

## 4. Deliberately open decisions

The following are not missing requirements. They are intentionally unresolved implementation/product decisions:

- exact launch Chinese translation witness list;
- exact provider for each witness;
- final production corpus/annotation release mix;
- final academic discovery MCP/provider set;
- final entitlement plans and pricing;
- final rights status of specific copyrighted source assets;
- final hosting region/topology inside the fixed security boundaries;
- optional model providers after Gemini;
- detailed Research Pro rollout order;
- final visual design details within the scholarly UX direction.

These must be resolved through later ADR/contract changes, not guessed by an AI builder.

## 5. Independent review conclusion

After creation and revision of `PROJECT_CHARTER.md`, the product intent is now substantially clearer than the implementation architecture alone.

A new developer should now be able to distinguish:

- product mission from implementation mechanism;
- mandatory scope from phased delivery;
- evidence from AI synthesis;
- source importance from machine-processing permission;
- published project rendering from external translations and user drafts;
- Research Pro from a second product;
- public BYOK from private authoring infrastructure;
- frozen requirements from intentionally open decisions.

Remaining uncertainty is primarily deliberate and documented rather than accidental.
